  `/api/talk`, `/api/worlds/{id}/talk/read-only`) ist doppelt gesperrt (AppAPI ADMIN plus

## Critical Issues

### CR-01: Ein früherer Verwalter bleibt im Schnappschuss: Kinderdaten, Talk-Räume und Freistellung ohne Adminrechte

**File:** `src/gameworld/notify/loop.py:369-384`, `src/gameworld/playtime/service.py:295-322` (Zeile 316), `src/gameworld/talk/service.py:277-304`, `src/gameworld/notify/loop.py:198-206, 219, 325`

**Issue:** `maintain_once` nimmt als handelndes Konto das alphabetisch erste Konto aus dem
gespeicherten Schnappschuss, nicht einen geprüften Verwalter:

```python
admins = sorted(parse_admins(raw))
acting = admins[0]
await TimeService(service, directory).refresh_admins(acting, blocking=False)
```

`refresh_admins` verlangt laut eigenem Docstring "Nur im Kontext eines geprüften Verwalters
aufrufen". `NcDirectory.group_members` antwortet Nicht-Admins mit 403
(`DirectoryUnavailableError`, directory.py:52-55, 81-88). Dann bleibt der alte Stand stehen
(service.py:312-315). Zusätzlich fügt Zeile 316 das handelnde Konto immer hinzu:
`sorted(set(members or ()) | {acting_uid})`.

Konkretes Szenario:

- Konten `anna` und `papa` sind in der Gruppe admin. `anna` wird aus admin entfernt oder gelöscht,
  etwa ein Ex-Partner oder ein versehentlich zum Admin gemachtes älteres Kind.
- Die 5-min-Wartung fragt weiter als `anna`, bekommt 403 und lässt `["anna","papa"]` stehen. Das passiert bei jedem Lauf.
- Geheilt wird der Stand nur, wenn ein echter Verwalter das Dashboard (`GET /api/worlds`,
  api/worlds.py:162) oder die Spielzeit-Seite öffnet. Die neuen Handy-Seiten (Pause, Versuch,
  Rückblick) frischen nicht auf. Ein Elternteil, das nur über Benachrichtigungen arbeitet,
  heilt den Zustand also nie.

Folgen, solange `anna` im Schnappschuss steht:

1. `anna` bekommt jeden Fremdversuch und den Tagesrückblick mit Spielminuten aller Kinder
   (`context.admins` als Empfänger, loop.py:177, 179, 335-337). Das ist ein Datenschutzleck.
2. `TalkService._sync_locked` setzt `want = set(access) | admin_set` (talk/service.py:202).
   `anna` wird in jeden Kinder-Raum geholt, zur Moderatorin hochgestuft und nach jedem Verlassen
   wieder hinzugefügt (Zeilen 216-227).
3. `reconcile_all` legt fehlende Räume mit `ensure_room(world.id, admins[0])` an (Zeile 304).
   `anna` wird dauerhaft Owner neuer Kinder-Räume. Nach D-27 bleibt ein Owner im Raum, der
   Abgleich entfernt Owner nie (Zeile 205).
4. Hat `anna` einen Spieler und ist eingeladen, bekommt sie die Zeile `frei` und ist von
   Pause und Zeitregeln ausgenommen (engine.py:399-402).
5. Nebenfolge: `_bot_room`, `_bot_person` und `_reviews` rufen Talk und Directory als
   `admins[0]` auf. Mit einem Nicht-Admin scheitern sie, der Bot wird still.

**Fix:** Hintergrundaufrufe nur mit einem Konto, das Nextcloud gerade als Admin bestätigt.
Das handelnde Konto nicht ungeprüft wieder einfügen.

```python
# playtime/service.py
async def refresh_admins(self, acting_uid: str, *, force: bool = False,
                         blocking: bool = True, verified: bool = True) -> bool:
    ...
    members = await self._directory.group_members(acting_uid, ADMIN_GROUP)
    found = set(members or ())
    if verified:
        found |= {acting_uid}   # nur aus require_verwalter-Kontext
    elif acting_uid not in found:
        return False            # Hintergrund: Konto nicht (mehr) admin, nichts schreiben
    value = json.dumps(sorted(found))

# notify/loop.py, maintain_once
for acting in sorted(parse_admins(raw)):
    try:
        if await TimeService(service, directory).refresh_admins(
            acting, force=True, blocking=False, verified=False) is not None:
            break               # erster Kandidat, dessen Gruppenabfrage gelingt
    except DirectoryUnavailableError:
        continue
```

Danach in `maintain_once`, `talk/service.py` und `notify/loop.py` das handelnde Konto nicht
starr als `admins[0]` wählen, sondern als erstes Konto, dessen Abfrage gelingt (wie
`_acting_members`). Zusätzlich sollten auch die Handy-Seiten (`/api/pause`, `/api/review`,
`/api/attempts`) `refresh_admins(uid, blocking=False)` mit dem geprüften `uid` aufrufen.
Ein Test sollte den Fall "erstes Konto im Schnappschuss verliert admin" abdecken.

## Warnings

### WR-01: Erneutes Auslösen während einer Pause kann sie sofort beenden oder "Für heute Schluss" verkürzen

**File:** `src/gameworld/playtime/pause.py:74-83, 166-174`

**Issue:** `start_window` behält bei laufender Pause `ab` und rechnet `bis = ab + minutes * 60`:

```python
ab = current.ab if current is not None and is_active(current, now) else now + PAUSE_LEAD_SECONDS
return ab, ab + minutes * 60
```

Szenario mit zwei Elternteilen: A startet um 18:00 eine 60-min-Pause (`ab` 18:00:30). B hat
die Pause-Seite offen, deren Abruf alle 15 s noch "keine Pause" zeigt, und tippt um 18:20 auf
"15 Minuten". Dann gilt `bis` = 18:15:30, liegt also in der Vergangenheit.

- `set_pause` speichert den Stand, die API antwortet `active: true, until_clock: "18:15"`.
- Der Lua-Mod lässt sofort alle wieder hinein (`t < pause.bis` ist falsch).
- Der Bot meldet "Pause bis 18:15 Uhr".

Genauso macht ein `POST /api/pause` während "Für heute Schluss" aus dem Schluss eine kurze
Pause (`art` wird `pause`), die womöglich schon abgelaufen ist. Eine Elternentscheidung
kippt also unbemerkt.

**Fix:**

```python
def start_window(now, minutes, current):
    if minutes not in PAUSE_MINUTES:
        raise ValueError(MSG_BAD_MINUTES)
    if current is not None and is_active(current, now):
        bis = max(current.bis, now + minutes * 60)   # nie verkürzen
        return current.ab, bis
    ab = now + PAUSE_LEAD_SECONDS
    return ab, ab + minutes * 60
```

Und in `PauseService.start`: Läuft schon ein Schluss, diesen behalten (oder 409 melden),
statt ihn auf `art="pause"` herabzustufen.

### WR-02: Der 10-Minuten-Hinweis mit Ton lässt sich durch Neuverbinden beliebig oft auslösen

**File:** `src/gameworld/notify/loop.py:258-264`, `src/gameworld/provisioner/time_mod.py` (Lua `warn`, etwa Zeilen 533-552, `register_on_leaveplayer` setzt `warned[name] = nil`), `src/gameworld/provisioner/access_mod.py:119` (`COOLDOWN = 2`)

**Issue:** Bei jedem Verlassen setzt der Mod die Warnmarken zurück. Bei 5 bis 10 Minuten
Rest erzeugt jeder neue Beitritt sofort wieder `hit == 600` und damit ein `warn10`-Ereignis.
`handle_warn10` sendet ohne Drossel mit `silent=False`. Anders als bei join und leave gibt
es kein `bot_presence`.

Ein eingeladenes Kind oder ein eingeladener Freund kann sich also alle paar Sekunden neu
verbinden (Wartezeit nur 2 s). Jedes Mal klingelt eine Talk-Nachricht auf allen Handys im
Raum, auch bei den Eltern. Das gilt auch für den Welt-Fenster-Grund (`why == "welt"`).

**Fix:** In `handle_warn10` je (Welt, Person, lokaler Tag) höchstens eine Nachricht senden,
etwa über `bot_presence` mit eigener Art oder über `daily_flags` mit dem Schlüssel
`warn10:<world>:<person>`. Erst beanspruchen, dann senden. Optional auch im Lua-Mod die
`warn10`-Ereignisse je Name und Tag merken.

### WR-03: Der Tagesrückblick kommt beim ersten Spielen nach der eingestellten Uhrzeit, mit Teildaten

**File:** `src/gameworld/notify/review.py:35-37`, `src/gameworld/notify/loop.py:300-337`

**Issue:** `review_due` prüft `local_minute >= pref_minute`. `_reviews` beansprucht nur,
wenn es Spielzeit gibt. Hat bis zur eingestellten Zeit niemand gespielt, bleibt der
Rückblick offen und wird beim ersten Takt mit Spielzeit gesendet.

Beispiel: Vorgabe 20:00, ein Kind fängt um 21:30 an. Um 21:30:05 kommt
"Heute gespielt: Lena 1 Min.", danach am selben Tag nichts mehr.

Bei einer früh eingestellten Uhrzeit (etwa 0:15 aus `reviewTimeOptions`) kommt der
"Abendrückblick" morgens nach der ersten Spielminute. Das widerspricht D-12, D-13 und D-14
("am Abend", Minuten je Kind des Tages).

**Fix:** Den Rückblick nur in einem kurzen Fenster nach der eingestellten Minute senden und
ohne Spielzeit für den Tag als erledigt merken:

```python
REVIEW_GRACE_MINUTES = 30
def review_due(local_minute, pref_minute, *, enabled):
    return enabled and pref_minute <= local_minute < pref_minute + REVIEW_GRACE_MINUTES
# in _reviews: ohne Spielzeit claim_review(uid, day) trotzdem setzen (ohne Versand)
```

### WR-04: Die Link-Basis überschreibt jeder Verwalterbesuch, eine Unterverzeichnis-Installation wird nicht unterstützt

**File:** `frontend/src/App.vue:66-69`, `src/gameworld/notify/links.py:17, 48-70`, `src/gameworld/notify/loop.py:105-114`

**Issue:**

1. Bei jedem Seitenaufruf eines Verwalters setzt `reportOrigin(window.location.origin)` die
   Basis aller Links neu. Ein einziger Besuch über eine LAN-Adresse (`http://192.168.1.10`)
   oder einen internen Hostnamen genügt, und ab dann zeigen alle Benachrichtigungen aller
   Verwalter dorthin. Unterwegs auf dem Handy öffnen die Links nicht mehr. `http` überschreibt
   dabei auch `https`.
2. `clean_origin` verbietet jeden Pfad und `EMBED_PATH` beginnt fest mit `/index.php/...`.
   Bei Nextcloud unter `https://example.org/nextcloud` zeigt jeder Link auf
   `https://example.org/index.php/...` und landet im 404. Auch `NEXTCLOUD_URL` mit Pfad fällt
   als Rückfall weg (dann wird gar nichts gesendet).

**Fix:** Origin nur speichern, wenn noch keiner gesetzt ist oder der Verwalter ihn ausdrücklich
übernimmt (Einstellung mit Anzeige). Den Webroot aus `@nextcloud/router` (`getRootUrl()`)
mitmelden und in `clean_origin` einen validierten Pfadanteil `^(/[A-Za-z0-9._~-]+)*$` zulassen.
`page_link` setzt dann `origin + webroot + EMBED_PATH` zusammen.

### WR-05: AsyncNextcloudApp-Sessions werden nie geschlossen (Stabilität, Ressourcen)

**File:** `src/gameworld/talk/rooms.py:112-115` (jeder Talk-Aufruf), `src/gameworld/talk/bot.py:87-90, 101-105`, `src/gameworld/notify/service.py:30-44`, `src/gameworld/access/roles.py:49-54`, `src/gameworld/access/directory.py:58-90`

**Issue:** Jeder Aufruf baut eine neue `AsyncNextcloudApp`. Laut nc_py_api `_session.py`
erzeugt das zwei niquests-`AsyncSession` (`adapter` und `adapter_dav`). `set_user` lädt
zusätzlich die Capabilities nach (`update_server_info`, nextcloud.py:510-518). Geschlossen
wird nichts.

Der 5-min-Talk-Abgleich braucht je Welt mindestens drei Clients (participants,
ensure_private, set_read_only), dazu Directory, Rollen und Benachrichtigungen. Die
Verbindungen räumt nur der GC ab. Unter Windows hat genau das den Prozess schon zum Absturz
gebracht (`.planning/debug/resolved/backend-windows-invalidstate.md`, bisher nur durch den
Selector-Loop umgangen). Unter Linux sammeln sich offene Sockets und ResourceWarnings, und
jeder Aufruf kostet einen zusätzlichen Capabilities-Request an Nextcloud.

Sicherheitsrelevant ist das nicht direkt. Für die Durchsetzung zählt es indirekt: Der Zeittakt
und der Notify-Loop laufen im selben Prozess, und wenn Dateideskriptoren ausgehen, trifft das
auch Docker-Aufrufe.

Einen Client über `set_user` zu teilen ist keine Lösung: `_add_auth` liest `self._user` erst
beim Request, gleichzeitige Coroutinen würden sich die Identität gegenseitig umschalten.

**Fix:** Einen gemeinsamen Kontextmanager nutzen und alle Stellen darauf umstellen:

```python
# gameworld/nc.py
@asynccontextmanager
async def nc_as(uid: str | None = None) -> AsyncIterator[AsyncNextcloudApp]:
    nc = AsyncNextcloudApp()
    try:
        if uid:
            await nc.set_user(uid)
        yield nc
    finally:
        for name in ("adapter", "adapter_dav"):
            adapter = getattr(nc._session, name, None)  # noqa: SLF001
            if adapter is not None:
                with contextlib.suppress(Exception):
                    await adapter.close()
```

Danach `async with nc_as(acting_uid) as nc:` in rooms.py, bot.py, service.py, roles.py und
directory.py. In `NcTalkRooms` mehrere OCS-Aufrufe eines Ablaufs (create plus listable,
ensure_private) in einem Kontext bündeln.

### WR-06: Im Zeittakt ist nur ProvisionerError je Welt isoliert, eine andere Exception setzt alle Welten aus

**File:** `src/gameworld/worlds/service.py:436-470`

**Issue:** `tick_time` fängt bei `_book_ledger` und beim Rendern beziehungsweise Schreiben nur
`ProvisionerError`. Ein `sqlite3.OperationalError` ("database is locked", Timeout 10 s, bei
gleichzeitigen Schreibern aus Notify-Loop, API und Talk-Abgleich gut möglich) oder ein
`ValueError` aus `render_time_file` in Welt A bricht den ganzen Takt ab. Welt B, C und
folgende bekommen in diesem Takt keine Regeldatei und keine Ereignissammlung.
`time_forever` loggt und versucht es 15 s später erneut. Bei einem dauerhaften Fehler einer
Welt (etwa einer kaputten Zeile) bleibt die Durchsetzung neuer Regeln für alle Welten hinter
ihr in der Schleife stehen.

Die Pause selbst schreibt `apply_pause_sync` direkt. Neue Spielzeit-Regeln, das Ende einer
Pause nach Ablauf und Einladungen über den Takt hängen aber daran.

**Fix:** Je Welt breiter isolieren, ohne den Fehlertyp zu verschlucken:

```python
for row in running:
    try:
        data, changed = self._time.render(row.id)
        if changed:
            self._write_time(row.id, data)
    except (ProvisionerError, sqlite3.Error, ValueError) as exc:
        self._time.forget(row.id)
        LOG.warning("Welt %s: Regeldatei im Takt nicht geschrieben (%s)", row.id, type(exc).__name__)
```

Dasselbe für `_book_ledger` und `_collect_events`.

### WR-07: Selbst gewählte Anzeigenamen gehen ungefiltert mit "@" in Bot-Nachrichten (Erwähnungen)

**File:** `src/gameworld/notify/texts.py:92-102`, `src/gameworld/notify/loop.py:209-226`

### WR-08: Abnahme-Skripte enthalten weitere falsch grüne Prüfungen

**File:** `scripts/dev/acceptance-phase4_1.sh:494, 518, 579, 739, 793, 614-615, 639, 675, 687-691, 775-776, 836`, `scripts/dev/smoke-talk.sh:223-225, 291, 366, 373-374`

**Issue:** Mehrere Prüfungen bestehen auch dann, wenn der geprüfte Dienst gar nicht antwortet:

1. **Negativkontrollen mit `ne "${CODE}" 200`** (Kind setzt Origin, Kind ändert Rückblick,
   Kind startet Pause, Kind liest `/attempts` oder `/review`, smoke-talk Zeile 291): Ein
   abgestürztes Backend (AppAPI 500/503) oder ein curl-Fehler (`000`) gilt als "abgewiesen".
   Erwartet werden muss genau `403`. Außerdem wird nicht geprüft, dass sich der Zustand nicht
   geändert hat, etwa `meta link_origin` nach dem Versuch mit `http://evil.example`.
2. **`not result_is ... auth_accept`** (Zeilen 687-691, Groß/Klein-Variante und falsches
   Passwort): Ein `prober_error` (Welt nicht erreichbar) besteht. Erwartet werden sollte
   `denied` mit CASE_HINT beziehungsweise die konkrete Ablehnung.
3. **SQL-Gleichheit ohne Werteprüfung** (Zeilen 614-615, 639): Scheitert `sql` (2>/dev/null),
   sind beide Seiten leer und `eq "" ""` besteht. "time_usage steigt in der Pause nicht" ist
   dann unbelegt.
4. **`notif_count` gleich 0 bei gescheitertem Abruf** (Zeilen 675, 775-776): `notif_new`
   schreibt bei Fehlern `[]`. Ein 401 oder 404 der Benachrichtigungs-API ergibt also "kein
   Hinweis". Der HTTP-Code von `notif_fetch` wird nie geprüft.
5. **Zeile 836** `not matches "${ADMINS}" ...`: Ein leerer Schnappschuss (SQL gescheitert) besteht.
6. **smoke-talk.sh 366 und 373-374**: Laut eigenem Kommentar erreicht kein Webhook die ExApp im
   Dev-Stack. "Chatinhalt steht nicht im Log" und "gefälschter Aufruf erreicht die ExApp nicht"
   sind damit inhaltlich leer. `webhook_hits` liefert bei fehlender Logdatei auf beiden Seiten
   `""`, die Gleichheit besteht.

**Fix:** Negativkontrollen auf `eq "${CODE}" 403` umstellen. Für Werte einen Helfer wie
`num() { printf '%s' "$1" | grep -Eq '^[0-9]+$'; }` nutzen und vor jedem `eq` beide Seiten als
Zahl prüfen. In `notif_fetch` den HTTP-Code zurückgeben und `notif_count` bei Code ungleich 200
`x` liefern lassen. Leere Ergebnisse grundsätzlich als Fehlschlag werten. Die Webhook-Prüfungen
als "nicht prüfbar" ausgeben (`fail` oder ein eigener Zähler), statt sie zu bestehen.

### IN-04: Der Vorgabetag der Handy-Seiten kommt aus der Gerätezeitzone

**File:** `frontend/src/route.js:69-73`, `frontend/src/views/AttemptsView.vue` und `ReviewView.vue` (`localDay()`)
**Issue:** Ohne `tag` nimmt die Seite das Datum des Handys, das Backend rechnet in der
Haushalts-Zeitzone. Ein Elternteil auf Reisen sieht unter "Heute" den falschen Tag.
**Fix:** Ohne `tag` den Parameter weglassen und das Backend den heutigen Haushaltstag wählen lassen.

### IN-05: Die Drossel wird verbraucht, obwohl nichts gesendet wird

**File:** `src/gameworld/notify/loop.py:167-179`, `src/gameworld/worlds/store.py:881-922, 968-984`
**Issue:**
- `claim_attempt` setzt `notified = 1` auch dann, wenn `origin` fehlt oder der Schnappschuss
  leer ist. Die 5 Tageshinweise sind dann still verbraucht.
- Umgekehrt löscht `delete_notify_data` die `join_attempts` der Welt. Damit sinkt der
  Tageszähler und es gibt wieder neue Einzelhinweise.
**Fix:** Erst beanspruchen, wenn Empfänger und Origin vorhanden sind. Die Tageszählung in
`daily_flags` führen statt über `join_attempts`.

### IN-06: Die Talk-Wartung blockiert den Benachrichtigungs-Loop, Hook-Tasks werden beim Herunterfahren nicht beendet

**File:** `src/gameworld/notify/loop.py:387-403`, `src/gameworld/main.py:50-78`, `src/gameworld/talk/service.py:352-376`
**Issue:** `maintain_once` läuft inline. Ein langsamer Talk-Abgleich vieler Welten verzögert
Fremdversuch-Hinweise und Rückblick um diese Dauer. `TalkService._tasks` werden im Lifespan
weder abgewartet noch abgebrochen.
**Fix:** Die Wartung als eigenen Task mit Lock starten. Im Lifespan-`finally` die Talk-Tasks
abbrechen beziehungsweise `drain()` mit Timeout aufrufen.

### IN-07: Vor Phase 4.1 vorhanden: Der Groß/Klein-Hinweis verrät Fremden die Spielernamen eingeladener Kinder

**File:** `src/gameworld/provisioner/access_mod.py` (Lua `case_variant`, `return CASE_HINT .. variant`)
**Issue:** Wer den UDP-Port erreicht, probiert `lena` und bekommt den exakt geschriebenen
eingeladenen Namen zurück. Das liegt außerhalb des Phasen-Diffs, betrifft aber die
Kinder-Privatsphäre. Die Passwörter bleiben stark, darum kein Zugang.
**Fix:** Den Hinweis ohne Namen formulieren ("Achte auf Groß- und Kleinschreibung").

### IN-08: Body-lose POST-Routen und CSRF (nicht verifiziert)

**File:** `src/gameworld/api/pause.py:314-327`, `src/gameworld/api/talk.py:412-419`
**Issue:** `POST /api/pause/end`, `/api/pause/schluss` und `/talk/read-only` haben keinen Body.
Ob der AppAPI-Proxy das Nextcloud-requesttoken erzwingt und ob das Session-Cookie bei
Cross-Site-POST mitgeht (SameSite), wurde hier nicht geprüft. Falls nicht, könnte eine fremde
Seite eine Pause beenden.
**Fix:** Im Smoke-Test einen Cross-Origin-Formular-POST ohne requesttoken versuchen. Als
Härtung `Content-Type: application/json` oder einen eigenen Header verlangen.

### IN-09: Läuft eine Pause von selbst ab, meldet der Bot nichts

**File:** `src/gameworld/playtime/engine.py:333-342`
**Issue:** `_active_pause` räumt eine abgelaufene Pause ohne Outbox-Zeile weg. "Die Pause ist
vorbei." kommt nur bei "Weiter". D-23 verlangt das nicht ausdrücklich, für die Kinder im Raum
fehlt aber das Signal.
**Fix:** Beim Wegräumen je Welt `pause_end` in die Outbox legen, still wie bei "Weiter".

### IN-10: Ereignis-Zeitstempel ohne Plausibilitätsgrenze

**File:** `src/gameworld/events/parse.py:23-24, 36-52`
**Issue:** `at` darf zwölf Ziffern haben. Ein manipulierter Lua-Prozess (Defense-in-Depth, die
Datei gilt laut Docstring als unvertrauenswürdig) könnte `deny`-Zeilen mit Zukunftsdatum
schreiben. Diese `join_attempts` fallen nie unter die Bereinigungsfrist (`day < cut`). Ab dem
Jahr 10000 wirft `datetime.fromtimestamp` einen Fehler, je Zeile wird er abgefangen.
**Fix:** In `_collect_events` nur Ereignisse mit `now - 86400 <= at <= now + 300` übernehmen.
