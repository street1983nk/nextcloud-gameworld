# Phase 4.1 Plan 03: Pause per Verwalter-API mit Live-Nachweis Summary

Verwalter starten über `POST /api/pause` eine Pause von 15, 30 oder 60 Minuten für alle Welten. "Weiter" und "Für heute Schluss" gibt es ebenfalls. Der Zustand liegt neustartfest in SQLite und landet im selben Request als `@pause` (bei Schluss mit `@morgen`) in der Regeldatei jeder Welt. Welten mit altem Mod werden dabei automatisch neu gestartet. Der Live-Test zeigt gegen eine echte Luanti-Welt: Vorwarnung, Trennen, Join-Sperre, der Verwalter bleibt verbunden, und die Pause zählt nicht aufs Kontingent.

## Was gebaut wurde

- **Reine Logik** (`playtime/pause.py`): `start_window` (ab = jetzt + 30 s, bis = ab + Dauer; eine laufende Pause behält ab), `schluss_window` (bis = Beginn des nächsten lokalen Tages über `day_starts`), `is_active`, `morgen_minutes` (-1 kein Spieltag, 0 ganzer Tag, sonst Fensteranfang; Ferienplan über `plan_for`; Konten ohne Plan fehlen), `clock_text` (H:MM).
- **Zustand** (`store.py`): `get_pause`, `set_pause` (Upsert auf die eine Zeile), `clear_pause(ended_by=)`. Mit `ended_by` wird nur eine bis dahin abgelaufene Pause gelöscht. Eine eben neu gesetzte Pause bleibt also stehen.
- **Rendern** (`engine.py`): `render` liest die aktive Pause und baut daraus die `PauseLine`. Bei `schluss` kommen `@morgen`-Zeilen für die Kinder dieser Welt mit Plan dazu. Pause und Morgen-Minuten stehen im Cache-Schlüssel. Eine abgelaufene Pause fällt heraus (neue Generation, sonst gleiche Bytes) und wird gelöscht.
- **Ausrollen** (`WorldService.apply_pause_sync`): Alles läuft unter `mutation()`. Zuerst wird der Zustand gesetzt oder gelöscht. Dann geht `push_time` an jede Welt. Laufende Welten mit `_events_restart_needed` werden mit stop plus `_launch` neu gestartet, ohne Vorwarnung (D-25). Je Welt entsteht eine Outbox-Zeile: `pause_start` (detail = bis), `pause_schluss` oder `pause_end`. Fehler bleiben je Welt isoliert, geloggt werden nur Welt-ID und Fehlertyp.
- **API** (`api/pause.py`): `require_verwalter` gilt für den ganzen Router. `PauseIn` lässt keine Zusatzfelder zu (extra forbid, strict) und nimmt `minutes: Literal[15, 30, 60]` nur als echte JSON-Ganzzahl an. "30", 30.0 und true ergeben 422. `PauseOut(active, art, ab, bis, until_clock, worlds[id, name, applied, restarted])`. Es gibt keinen Nextcloud-Aufruf.

## Deviations from Plan

### Auto-fixed / ergänzt

**1. [Rule 1 - Bug] Strikte Prüfung von minutes**
- **Found during:** Task 2
- **Issue:** `Literal[15, 30, 60]` nahm auch im strict-Modell 30.0 an (Literal-Vergleich per Gleichheit). `Field(strict=True)` geht bei Literal nicht (RuntimeError in pydantic).
- **Fix:** Zusätzlicher `BeforeValidator`, der nur `type(value) is int` durchlässt. Der Test deckt 30.0 und true ab.
- **Commit:** 2a6d6a1

**2. [Rule 2 - Korrektheit] Kein falsches "Pause vorbei"**
- "Weiter" ohne laufende Pause legt keine Outbox-Zeile an. Sonst hätte der Bot in 04.1-06 grundlos "Die Pause ist vorbei." gemeldet.

**3. Signatur apply_pause_sync**
- Der Plan sah `apply_pause_sync(state_or_none, outbox_kind, detail)` vor. Umgesetzt ist `apply_pause_sync(decide, outbox_kind)`: Die laufende Pause (für "ab bleibt") wird so unter derselben Sperre gelesen, unter der sie gesetzt wird. detail ergibt sich aus dem Zustand. Verhalten wie im Plan.

**4. Prozess:** Ein Hilfsaufruf `uv run python -` (stdin) blieb während Task 1 hängen und wurde beendet (nur dieser Prozessbaum). Danach liefen alle Hilfsskripte als Datei mit `python -I`. Auf den Code hatte das keine Auswirkung.
